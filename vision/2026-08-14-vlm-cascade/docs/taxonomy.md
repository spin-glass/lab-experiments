# taxonomy.md — 分類体系・アノテーション・カスケード統合の設計ノート

設計文書 v0.1（2026-08-21）。クラス定義の正本は `taxonomy/taxonomy.yaml`（本書時点では未コミット。導入は M0）。本書は設計判断とその根拠の記録であり、定義の詳細は正本を参照する（重複記載しない）。

アーキテクチャ全体・マイルストーン・decision matrix の正本は [design.md](design.md)。本書は design.md の「分類体系」の部分を詳細化するものであり、矛盾した場合は design.md を先に改訂する。

## 0. 要旨

レストラン写真分類（Yelp Open Dataset 5クラス: food / drink / menu / inside / outside）の主課題である「food への誤分類」に対し、フラットな二値フラグ（food / not-food）ではなく2階層タクソノミーを導入する。第1階層（food / non-food）が二値フラグをそのまま吸収し、「food でない」という否定を非 food 側の肯定クラスの列挙に変換する。これは CLIP 系エンコーダが否定表現をほぼ扱えないことへの処方箋であり、food に間違われやすい対象は「正しい親の下の肯定サブクラス」（誤爆吸収クラス）として明示的に命名する。

アノテーションでは第2階層（運用クラス）のみを記録し、第1階層は parent() で導出する。画像の判定可能性（品質）と判定者の迷い（不確実性）は内容分類と直交する別フィールドに分離し、残余クラスへ流し込まない。体系の記述は SKOS の項目名を借用した YAML 1ファイルを単一の正とし、検証・SKOS/Turtle・ラベルマスタ・プロンプト集・可視化をすべて自動生成する。

## 1. 課題と方針

zero-shot 分類で food の precision が問題になるとき、素朴な対策は「food か否か」の二値フラグの前置である。しかし「food 以外」はメニュー・店内・人物などの視覚的に異質な寄せ集めで、単一プロンプト・単一境界では表現しにくい。タクソノミーはこの否定を肯定同士の弁別に置き換える。二値フラグは捨てるのではなく、階層の第1分割としてそのまま吸収される。

階層をスコアリングに使う方式は CHiLS [CHiLS23] の系譜に立つ。抽象的なクラス名（inside 等）に弱く具体名詞に強いというエンコーダの性質に対し、親の下にサブクラスを置いて子でスコアリングし親へ集約（max）することで、追加学習なしに zero-shot 精度を改善できる。フラット5クラスとの優劣は M1 で実測して決める（D11）。

## 2. 設計原理

階層は is-a（〜の一種）関係のみで組む。part-of（〜の一部）を混入させると親に書いた定義・規則の継承が壊れる。分割は3原則に従う: 同一レベルは単一の分割基準で割る、同レベルの子は相互排他、子の合併が親を網羅する [Hedden22]。

既存の5クラスはこの原則の観点では複数ファセットの混合である。food / drink は被写体の種類、menu は文書種別、inside / outside は撮影視点に属し、単一の木としては分割基準が交差している。したがって「店内で撮られたメニュー」のような複属事例は偶然ではなく構造的必然として発生する。本設計はこれを木の再設計で消そうとせず、優先規則（判定質問の順序）を「多ファセット空間から単一ラベルへの射影」として明示化して受け止める。順序を変えるとラベルが変わるため、**優先規則はアノテーション開始前に確定し、バージョン管理する**。優先規則の置き場は `rulebook.md`（design.md §4 の (c)）であり、タクソノミー側は運用クラス集合を提供し、build 時に「優先規則が第2階層を過不足なく被覆すること」を検証する（§6）。

残余クラス（other）を導入する場合、その外延は他クラスの定義の否定として決まる。他クラスの定義やサブクラスを変更すると残余の外延も変わるため、変更のたびに残余の再検証が必要になる。これがタクソノミーに版番号と変更記録を刻む実務上の理由である。

## 3. 2階層タクソノミー

構造は「全画像 → 第1階層（food ブランチ / non-food ブランチ）→ 第2階層（運用クラス）→ 第3階層（プロンプト用サブクラス）」。

| 階層 | 役割 | ゴールドへの記録 | 例 |
|---|---|---|---|
| 第1階層 | 二値フラグの吸収先 | しない（導出） | food / non-food |
| 第2階層 | 運用ラベル | する | food, drink, menu, inside, outside（残余 other は拡張オプション） |
| 第3階層 | Stage 1 プロンプト・分析用 | 任意（即答できる場合のみ併記） | food 細分（麺類・デザート等）、誤爆吸収クラス |

誤爆吸収クラスは「food に間違われやすい対象」を正しい親の下の肯定クラスとして命名したもので、例として、料理写真入りメニューページ（親: menu）、店頭の料理ディスプレイ（親: outside）、料理の載ったテーブルを含む店内カット（親: inside）、食事中の人物（親: inside または残余）を置く。この列挙はデータセット依存であり、food 予測画像のサンプル手集計（precision 監査、100枚程度。M1）で漏れ元の内訳を取り、経験的に発見・追加していく（D13）。

否定を使わない理由は機構的である。CLIP の対照事前学習で使われるキャプションは「写っているもの」しか記述しないため、テキスト埋め込み空間に否定の幾何がほぼ育たない。"not food" を学習させる代わりに、非 food 側を具体物の肯定列挙で持ち、肯定同士の弁別に帰着させる。

## 4. 属性・品質・不確実性の分離

「food が写っているか」（属性）と「この画像のクラスは food か」（分割）は別の問いである。料理写真が大きく載ったメニューページは属性 Yes・クラス menu となり、属性基準で二値ラベルを作ると運用ラベルと矛盾するペアが量産される。整合条件は level1 = parent(level2) であり、これを守るために第1階層は記録せず導出のみとする。

同様に、残余クラスに意味を混載しない。内容の残余（明確にどのクラスでもない）、判定不能（品質起因で内容が判別できない）、判定者の迷い（境界事例）は直交する3概念であり、混ぜると残余クラスのプロンプトが書けなくなり、評価も壊れる（ボケた麺の写真を food と当てた予測が減点される等）。記録スキーマは次のとおり（design.md §5 の `gold_annotations` に対応）。

| フィールド | 値 | 意味 |
|---|---|---|
| content_label | 第2階層クラス or unjudgeable | 内容の分類 |
| quality | ok / degraded / unjudgeable | 判定可能性。基準は「運用クラスのどれか判別できるか」であり、ボケ量そのものではない |
| boundary_flag | bool | 判定者の迷い。付けたら仮ラベルのまま先へ進み、後で境界事例集（rulebook.md (d)）へ |
| food_visible | bool | 属性の正式フィールド化（分割と別軸で保持） |
| secondary | クラス名（任意） | 顕著な副被写体。「food は写っているが主被写体でない」画像を hard スライスとして切り出せる |

対象外（5 クラスのどれにも該当しない）画像はアノテーション専用の残余値 out_of_scope として scope_annotations（design.md §5）に記録し、Stage1 のクラスや残余クラスへは流さない（G0 / D14）。

`boundary_flag` は人のアノテーション側の不確実性であり、予測側の `flag ∈ {clear, rule_resolved, irreducible}`（design.md §4）とは別物。前者はゴールド作成時、後者はカスケード出力時に付く。

運用出力は導出で作る: quality が unjudgeable なら残余（または除外。運用先は要決定事項 D13）、それ以外は content_label。導出は細→粗の一方向にしか効かないため、記録は常に細かい方で行う。評価は内容精度（unjudgeable 除外）と運用出力精度（導出込み）の2系統に分かれる。

曖昧さの経路も対称に設計する。人の迷いは boundary_flag と優先規則による強制単一化で処理し、モデルの迷いは Stage 3 委譲で処理する。どちらも残余クラスへ流さない。複数物体は優先規則が射影装置として処理するため、必要なのは主被写体の操作的定義（面積 → 中心性 → 撮影意図＝ピントの合っている対象）だけである。同格衝突（food と drink が同格で写る等）は優先順位で機械的に決め、その順序自体を開始前に確定する。

アノテーション運用は2パス制とする: 50〜100枚のパイロット → 迷いの収穫とガイドライン改訂 → 本番（M4）。現実とのギャップは事前に潰しきれないため、回収の仕組みで管理する。

## 5. カスケード統合

### Stage 1（エンコーダ zero-shot）

葉（第3階層）ごとにスコアを取り、ブランチ内 max で集約して S_food と S_non を得る。マージン m = S_food − S_non を第1階層の確信度（`branch_margin`）とし、|m| が大きくかつ葉 argmax の親が第1階層判定と一致する場合のみ確定、そうでなければ Stage 3（VLM）へ委譲する。二値判定で先に弾く直列ハードゲートは置かない。food を誤ゲートすると葉では回収不能になるためで、ソフトスコアを保持し高確信のみ確定する（D12）。閾値は自然分布スライスで food precision 寄りに較正する。

学習前に実行できる最安の診断がプロンプト埋め込みの余弦類似度行列である。画像不要・テキスト埋め込みのみで、兄弟プロンプト同士の過接近や、誤爆吸収プロンプトが親クラスより food 側に寄っている等の混同の予兆を事前検出し、プロンプト文の書き換えで埋め込みの幾何を直す。M1 の最初に回す実験として位置づける。

### Stage 2（決定的ルール層）

Stage 2 はポリシー層であり、品質規則と運用写像の管轄はタクソノミーでなくここに置く。ボケ判定は Laplacian 分散等の決定的信号で機械化でき、メニュー起因の誤爆は OCR テキスト被覆率でほぼ決定的に潰せる。規則の変更は3層変更ポリシー（design.md M7: 境界事例追記／新規追加／既存修正）で統治し、タクソノミー側は scopeNote から規則を参照するだけに留めてクラス定義を汚さない。**語彙（何があるか）と割当規則（どう写像するか）の分離**が原則であり、これが `taxonomy.yaml`（語彙）と `rulebook.md`（ポリシー）を分ける根拠である。

### Stage 3（VLM 委譲）

分業の非対称を活かす。エンコーダに渡せるのは肯定プロンプトだけだが、VLM には定義・scope note・優先規則・否定・例外をすべて渡せる。正本 YAML の定義文と rulebook の優先規則が、そのまま VLM プロンプトの原稿になる。シルバーセット（軽量 VLM の多数決）は階層でバックオフできる: 葉で不一致でも第1階層で一致していれば二値シルバーとして採用し、捨てない。第1階層の学習データを安く増やす手段になる。

### fine-tuning への接続（M6）

階層を負例の難度マップとして読む。第1階層境界（food 葉 × 誤爆吸収クラス）が hard negative の主戦場であり、ブランチ内兄弟（麺類 × 丼等）は細粒度弁別用。バッチ内の吸収クラス混入比率、hard negative 比率のカリキュラム、温度との相互作用はいずれも階層から導出できる設計ノブである。sigmoid 損失（SigLIP 系 [SigLIP2-25]）はペアが独立なため、タクソノミー距離による負例の重み付けを batch-softmax の結合なしに素直に書ける。ゴールドが数千枚規模のうちは、フル微調整よりも linear probe / LoRA [LoRA21] と WiSE-FT 補間 [WiSE22]（zero-shot 頑健性の保持）が現実解となる。

### 逆方向: データからの体系拡張

クラス内の CLIP 画像埋め込みをクラスタリング（k-means、粗→細なら残差量子化）し、クラスタを人が命名して YAML へ追記する。残差量子化の各段が階層のレベルに対応する点で、生成的検索の Semantic ID [TIGER23] と同型であり、知見が相互に転用できる。誤爆画像は LeGrad [LeGrad24] 等の帰属可視化で「画像のどこに反応したか」を示し、ルール（OCR 被覆率等）の根拠画像として記録する（画像そのものは reports に掲載しない。CLAUDE.md 絶対制約）。

## 6. データ表現と実装

正本は SKOS [SKOS09] の項目名を借用した YAML 1ファイルとする。SKOS は統制語彙・タクソノミーを Web 上で機械可読に記述する W3C 標準（2009年勧告）で、概念を OWL クラスではなくインスタンスとして扱う軽量モデルである。借用する項目は prefLabel（正式名）、altLabel（言語タグで英語の CLIP 用プロンプト群を同一概念に束ねる）、definition、scopeNote、broader、changeNote。構造制約（排他・網羅・導出式）は SKOS に枠がないため YAML 専用ブロックに置く。フル実装（トリプルストア運用等）は採らず、項目名の借用と Turtle への出口の保持に留める。

`taxonomy/` 配下の構成:

| ファイル | 役割 |
|---|---|
| taxonomy.yaml | 正本。編集はこのファイルのみ。`scheme.version` が `taxonomy_version` |
| taxonomy_build.py | 検証 + 生成（taxonomy.ttl / label_master.csv / prompts.json） |
| taxonomy_viz.py | 検証 + 可視化（taxonomy_tree.md / taxonomy.svg） |
| taxonomy.ttl | 生成物。SKOS/Turtle。標準形式への出口（rdflib で往復パース確認） |
| label_master.csv | 生成物。アノテーション用マスタ。第1階層は導出列（二重付け禁止の実装） |
| prompts.json | 生成物。第2階層クラスごとに自身と子のプロンプトを source 付きで集約。`gen_from_rulebook.py` の Stage1 プロンプト入力 |
| taxonomy_tree.md | 生成物。Mermaid 図入り Markdown（GitHub がそのまま描画） |
| taxonomy.svg | 生成物。Graphviz 出力 |

検証項目は、id と prefLabel の一意性、broader 参照先の存在、階層規則（第1階層は無親・第2階層の親は第1階層・第3階層の親は第2階層）、第2階層がちょうど運用クラス数であること、rulebook の優先規則が第2階層を過不足なく被覆すること、各運用クラスにプロンプト源（自身または子）が存在すること。検証に1件でも失敗すると生成せず異常終了する。参照をわざと壊した入力で生成が止まる負のテストを pytest に含める。

運用ルールは3つ。YAML を変更したら build と viz を両方実行する（Makefile または pre-commit に束ねる）。版は scheme.version と changeNote で刻み、runs / reports に `taxonomy_version` として記録する。既存ツールの補足として、SKOS Play（LGPL-3.0、セルフホスト可）や Skosmos（OSS）等の可視化・公開ツールが存在するが、本規模（十数概念）では正本からの自動生成で足りる。

結合キーは node_id に統一する。プロンプト・ルールの対象ノード・評価スライス・実験レポートを同一 id で結合し、ウェアハウス側に ancestors 配列を1列持てば「food の全子孫」のような推移閉包が1クエリで取れる。知識表現の観点では taxonomy.ttl がスキーマ（TBox）、画像レコード（content_label, quality, boundary_flag, run_id, git sha 等）が事実（ABox）に相当し、体系全体が小さなナレッジグラフとして成立している [KG21]。将来、画像以外のエンティティ（店舗・ジャンル・メニュー）へ拡張する場合もこの主キー設計がそのまま土台になる。

## 7. 採用済み設計判断（T1–T10）

design.md §8 の D 系は「分析で決める判断」であるのに対し、以下は本書の時点で根拠をもって採用した判断である。覆す場合は本書を改訂し changeNote に記録する。分析で決めるものは D11–D13 として design.md の decision matrix に登録した。

| ID | 判断 | 根拠 |
|---|---|---|
| T1 | 二値フラグを第1階層として吸収 | 否定を肯定列挙へ変換（エンコーダの否定不能性）。フラグ単独では非 food が非一貫集合になる |
| T2 | 第1階層は記録せず導出のみ | 属性と分割の混同による矛盾ペア量産の防止。整合条件 level1 = parent(level2) |
| T3 | 誤爆を肯定サブクラスとして命名 | hard negative の明示列挙。プロンプト化・学習資産化が可能 |
| T4 | 直列二値ゲート不採用、ブランチマージン方式 | 誤ゲートは葉で回収不能。ソフトスコア保持と高確信のみ確定（実測比較は D12） |
| T5 | 品質・不確実性を内容と直交分離 | 残余クラスの意味純度の維持。評価2系統の成立 |
| T6 | 「曖昧なら残余へ」の運用不採用 | 人は boundary_flag、モデルは委譲、の対称設計 |
| T7 | SKOS は項目借用に留める | 費用対効果。Turtle 生成で標準への出口は保持 |
| T8 | 正本 YAML、生成物は全自動生成 | 置き場の一意性。検証通過を生成の前提条件にできる |
| T9 | 品質規則・運用写像・優先規則はポリシー層（rulebook.md / Stage2）へ | 語彙と割当規則の分離。3層変更ポリシーで統治 |
| T10 | サブクラス発見は埋め込みクラスタリングで経験的に | 実データ検証。残差量子化＝Semantic ID と同型で知見転用 |

## 8. 未決事項と次アクション

未決は2件（D13 として decision matrix に登録）: food と drink が同格で写る場合の優先順位（現行案は food 優先）、および quality が unjudgeable の画像の運用出力先（残余か除外か）。いずれも M4 パイロットアノテーションで確定後に YAML v0.2（quality 軸・operational_mapping・記録スキーマの追記）と rulebook へ反映し changeNote に記録する。

次アクションとマイルストーンの対応:

1. `taxonomy/` の導入、build / viz の Makefile / pre-commit への束ね — M0
2. プロンプト類似度行列の診断（テキストのみ・最安） — M1 冒頭
3. food 予測画像の precision 監査 100枚程度、誤爆吸収クラスの初期列挙 — M1
4. 50〜100枚のパイロットアノテーションによる2パス目のガイドライン改訂 — M4
5. 未決2件の確定と YAML v0.2 — M4 終了時
